# 🎬 **Talk&Watch — Мессенджер для совместного просмотра видео**

## 📱 **О чем проект**

**TalkAndWatch** — это мессенджер, в котором можно не только переписываться, но и смотреть видео синхронно с собеседником.

**Простыми словами:** Это как Telegram, но внутри каждого чата есть кнопка "Пойдем посмотрим вместе". Нажимаешь — и вы с другом смотрите YouTube видео одновременно, видите реакции друг друга в реальном времени и можете обсуждать прямо во время просмотра.

**Для кого:**
- Пары на расстоянии (хотят смотреть сериалы "как вместе")
- Друзья из разных городов (совместный просмотр мемов, стримов)
- Семьи с родственниками в других городах (семейные видео)
- Учебные группы (совместный просмотр лекций)

---

## 🏗️ **Архитектура проекта**

### **3 микросервиса:**

### **1. Auth Service (Сервис авторизации)**
**Что делает:**
- Регистрация и вход пользователей
- Выдача JWT токенов
- Хранение профилей пользователей

**Технологии:** Node.js, PostgreSQL, JWT
**API:** REST (регистрация, логин, профиль)

### **2. Chat Service (Сервис чатов)**
**Что делает:**
- Личные и групповые чаты
- Отправка сообщений в реальном времени (WebSocket)
- История сообщений
- Приглашения в комнаты просмотра

**Технологии:** Node.js, MongoDB, WebSocket (Socket.IO)
**API:** REST (создание чата, список чатов) + WebSocket (сообщения)

### **3. Video Room Service (Сервис видеокомнат)**
**Что делает:**
- Создание комнат просмотра внутри чатов
- Синхронизация видео (play, pause, seek)
- Очередь видео
- Участники комнаты

**Технологии:** Node.js, Redis (состояние комнат), WebSocket (синхронизация)
**API:** REST (создание комнаты, добавление видео) + WebSocket (синхронизация)

## 🔧 **Что реализовано (по пунктам)**

### **Блок 1: Межсервисное взаимодействие**
- ✅ **API Gateway (Nginx)** — единый вход для всех сервисов (порт 8080)
- ✅ **Message Broker (RabbitMQ)** — асинхронные события между сервисами
- ✅ **Event-Driven паттерн** — события с несколькими подписчиками

**Как работает:**
```
Когда пользователь создает комнату:
1. Video Room Service публикует событие "room.created" в RabbitMQ
2. Подписчик 1 (Chat Service): пишет в чат "Комната создана, присоединяйтесь!"
3. Подписчик 2 (Auth Service): обновляет статистику пользователя
4. Подписчик 3 (Video Service): инициализирует состояние комнаты
```

### **Блок 2: Данные и согласованность**
- ✅ **Database per Service** — у каждого сервиса своя БД
- ✅ **Миграции БД (Flyway)** — версионирование схемы PostgreSQL
- ✅ **Eventual Consistency** — события доставляются асинхронно
- ✅ **CQRS** — разделение чтения/записи для списка чатов
- ✅ **Inbox Pattern** — защита от дубликатов сообщений
- ✅ **Redis Cache** — хранение состояния комнат и кеширование

**Как работает CQRS:**
```
Запись: сообщения сохраняются в MongoDB (медленно, но надежно)
Чтение: последние 50 сообщений хранятся в Redis (быстрый доступ)
При запросе чата: берем из Redis, если нет — из MongoDB
```

### **Блок 3: Отказоустойчивость**
- ✅ **Структурированное логирование (JSON)** — все логи в JSON формате
- ✅ **Health Checks** — /health эндпоинты у всех сервисов
- ✅ **Graceful Shutdown** — корректное завершение при остановке
- ✅ **Correlation ID** — сквозной ID запроса через все сервисы
- ✅ **Централизованный сбор логов (Loki + Promtail)**
- ✅ **Метрики Prometheus + Grafana** — дашборд с метриками
- ✅ **Таймауты** — на все внешние вызовы

**Что логируем:**
```json
{
  "timestamp": "2024-01-15T20:00:00Z",
  "level": "info",
  "service": "video-room",
  "correlation_id": "req_123456",
  "message": "User joined room",
  "user_id": 42,
  "room_id": "room_789"
}
```

### **Блок 4: Безопасность и продакшн**
- ✅ **Переменные окружения** — вся конфигурация через .env
- ✅ **Docker Compose** — запуск одной командой
- ✅ **.env.gitignore** — секреты не в репозитории
- ✅ **Swagger/OpenAPI** — документация API
- ✅ **JWT аутентификация** — защита всех эндпоинтов
- ✅ **CI/CD (GitHub Actions)** — автосборка и тесты
- ✅ **Feature Flags** — включение/выключение фич

## 🎮 **Сценарии использования**

### **Сценарий 1: Регистрация и вход**

**Как это работает:**
1. Пользователь открывает приложение
2. Вводит email и пароль → POST /auth/register
3. Auth Service создает пользователя в БД
4. Возвращает JWT токен
5. Все следующие запросы идут с токеном в заголовке

**Технически:**
- REST API, синхронный вызов
- Пароль хешируется (bcrypt)
- JWT содержит id пользователя и роль (user/admin)

---

### **Сценарий 2: Создание чата и приглашение друга**

**Как это работает:**
1. Пользователь нажимает "Создать чат"
2. Вводит email друга → POST /api/chats
3. Chat Service создает чат в БД
4. Публикует событие "chat.created" в RabbitMQ
5. Друг получает уведомление (через WebSocket)

**Технически:**
- Синхронный REST запрос
- Асинхронное событие в брокер
- Event-Driven: несколько подписчиков

---

### **Сценарий 3: Совместный просмотр видео (главный сценарий)**

**Как это работает:**

**Шаг 1 — Создание комнаты:**
1. В чате с другом нажимаем "🎬 Смотреть вместе"
2. POST /api/rooms → Video Room Service
3. Video Room Service создает комнату в Redis
4. Публикует событие "room.created" в RabbitMQ
5. Chat Service получает событие и пишет в чат: "Антон создал комнату для просмотра"
6. Друг получает WebSocket уведомление

**Шаг 2 — Добавление видео:**
1. Вставляем ссылку на YouTube → POST /api/rooms/123/videos
2. Video Room Service добавляет видео в очередь (Redis)
3. Через WebSocket всем участникам приходит событие "video.added"
4. У всех в плеере появляется видео

**Шаг 3 — Синхронизированный просмотр:**
1. Я нажимаю Play → WebSocket событие "player.play"
2. Video Room Service получает, обновляет состояние в Redis
3. Рассылает всем участникам комнаты (кроме отправителя)
4. У друга видео запускается автоматически
5. Я перематываю на 5:30 → событие "player.seek" — у всех перемотка

**Шаг 4 — Чат во время просмотра:**
1. Я пишу сообщение в чат комнаты
2. WebSocket событие "room.message"
3. Chat Service сохраняет сообщение в MongoDB
4. Все участники видят сообщение поверх видео

**Шаг 5 — Завершение:**
1. Закрываем комнату
2. Video Room Service удаляет состояние из Redis
3. Публикует событие "room.closed"
4. Chat Service пишет: "Просмотр завершен"
5. Возвращаемся в обычный чат

**Технически в этом сценарии задействовано:**
- ✅ Все 3 сервиса
- ✅ REST API
- ✅ WebSocket (real-time)
- ✅ Message Broker (события)
- ✅ Redis (состояние комнат)
- ✅ Correlation ID (отслеживание запроса)
- ✅ JWT (проверка прав)

---

### **Сценарий 4: Администратор модерирует чат**

**Как это работает:**
1. Администратор заходит в любой чат
2. Видит сообщение с нарушением
3. Нажимает "Удалить" → DELETE /api/messages/123
4. Chat Service проверяет роль из JWT (admin)
5. Удаляет сообщение
6. Публикует событие "message.deleted"
7. У всех участников сообщение исчезает
