# Лабораторная работа №1: Проектирование микросервисной архитектуры

## 1. Цель работы
Спроектировать архитектуру микросервисной системы, которая будет реализована в Лабораторной работе №2. Научиться принимать архитектурные решения, обосновывать выбор паттернов и анализировать компромиссы (trade-offs), присущие распределенным системам.

## 2. Описание задания
Необходимо спроектировать систему, состоящую из **3–5 микросервисов**, которая в дальнейшем может быть развернута на одной машине с помощью Docker Compose или Minikube.

### Доступные темы
1.  **E-commerce платформа**
    - *Сервисы:* каталог товаров, корзина, заказы, платежи, доставка.
    - *Фичи:* просмотр каталога, добавление в корзину, оформление и оплата заказа.
2.  **Онлайн-обучение**
    - *Сервисы:* курсы, студенты, прогресс обучения, сертификаты, видео.
    - *Фичи:* просмотр курсов, прохождение уроков, выдача сертификатов.
3.  **Социальная сеть**
    - *Сервисы:* пользователи, посты, лента новостей, лайки/комментарии, нотификации.
    - *Фичи:* публикация постов, лента друзей, уведомления о активностях.
4.  **Своя тема**
    - Требуется согласование с преподавателем.
    - Тема должна быть достаточно сложной, чтобы оправдать использование микросервисной архитектуры.

### Технические ограничения (Constraints)
- Количество микросервисов: **от 3 до 5**.
- Система должна быть рассчитана на запуск на одной машине (Docker Compose / Minikube).
- Обязателен принцип **Database per Service** (у каждого сервиса своя БД).
- Наличие минимум **одного асинхронного взаимодействия** (через message broker).
- Наличие минимум **одного синхронного взаимодействия** (HTTP/gRPC).

## 3. Результат работы (Deliverables)
Итоговый проект должен представлять собой документ, содержащий следующие 6 обязательных разделов.

### Раздел 1. Функциональные требования (Functional Requirements)
В этом разделе нужно описать, что именно будет делать система с точки зрения пользователя.

- **Список фич (5–7 штук):** Перечислите ключевые возможности, которые будут реализованы в системе (например: регистрация, поиск товаров, оформление заказа).
- **User Flows (2–3 основных сценария):** Опишите пошагово, как пользователь будет выполнять ключевые задачи. Например: *"Пользователь ищет товар → добавляет в корзину → оформляет заказ → оплачивает → получает подтверждение"*.
- **Out of scope:** Четко обозначьте, какие функции сознательно останутся за рамками проекта (например: «Не реализуем возврат товаров, отзывы и систему лояльности»).

### Раздел 2. Нефункциональные требования (Non-Functional Requirements)
В этом разделе описываются качественные характеристики системы и архитектурные ограничения.

- **Модель согласованности (Consistency):**
    - Где критически важна **strong consistency** (немедленная актуальность данных) и почему? (Например: остатки товаров, платежи).
    - Где допустима **eventual consistency** (возможна задержка в синхронизации) и почему? (Например: уведомления, статистика просмотров).
- **Синхронное и асинхронное взаимодействие:**
    - Какие операции будут выполняться **синхронно** (HTTP/gRPC) и почему?
    - Какие операции будут выполняться **асинхронно** (через брокер сообщений) и почему?
- **Требования к задержкам (Latency):**
    - Какие операции должны выполняться быстро (например, <100 мс, <500 мс)?
    - Какие операции могут выполняться долго (например, >1 секунды)?
    - Обоснуйте, как это влияет на пользовательский опыт (UX).
- **Масштабируемость (Scalability):**
    - Какие сервисы будут самыми нагруженными и почему?
    - Где могут возникнуть узкие места при росте числа пользователей?
    - Какие стратегии масштабирования (вертикальное/горизонтальное) планируется применить?

### Раздел 3. Архитектурная диаграмма
Визуальное представление системы, на котором должны быть отражены:

- **Микросервисы:** Прямоугольники с названиями и кратким описанием зоны ответственности (bounded context).
- **Базы данных:** Какая БД (и какого типа: PostgreSQL, MongoDB, Redis) принадлежит какому сервису.
- **Брокер сообщений:** Если используется асинхронная коммуникация (RabbitMQ, Kafka).
- **Кеш (Cache):** Если планируется использование Redis, Memcached и т.д.
- **API Gateway:** Единая точка входа для клиентов (если планируется).
- **Связи:**
    - **Сплошная стрелка** — синхронный вызов (HTTP/gRPC).
    - **Пунктирная стрелка** — асинхронное событие.
    - На стрелках должны быть подписи (какая информация передается).

*Инструменты:* draw.io, Excalidraw, Miro, PlantUML или даже фото рисунка от руки.

### Раздел 4. Модель данных и API (Data Model & API)
Описание структур данных и контрактов взаимодействия.

- **Модель данных (Data Model):**
    - Для каждого сервиса перечислите ключевые сущности (entities) и их поля (3–7 полей).
    - Опишите связи между сущностями внутри одного сервиса.
    - Важно указать **владение данными (ownership)**: какой сервис является источником истины для тех или иных данных.
- **API (контракты между сервисами):**
    - Опишите 5–7 ключевых точек взаимодействия (эндпоинтов или событий).
    - Для **синхронных вызовов** укажите: HTTP метод, путь, формат запроса (request body) и ответа (response body), а также какой сервис вызывает какой.
    - Для **асинхронных событий** укажите: название события, сервис-издатель (publisher), сервис-подписчик (consumer) и структуру данных (payload).

### Раздел 5. Компромиссы и обоснование решений (Trade-offs)
Этот раздел демонстрирует понимание архитектуры. Необходимо развернуто ответить на следующие вопросы:

1.  **Декомпозиция:** Почему система разбита на сервисы именно так? По какому принципу выделены границы контекстов? Рассматривались ли альтернативные варианты?
2.  **Выбор коммуникации:** Почему для конкретных операций выбран синхронный или асинхронный способ? Что произойдет, если сделать наоборот?
3.  **Анализ проблем:** Какие проблемы могут возникнуть в работе системы?
    - Что если один из сервисов или брокер сообщений станет недоступен?
    - Что если база данных перегружена?
    - Какие сложности создает eventual consistency?
4.  **Стратегии решения проблем:** Как вы планируете бороться с описанными рисками?
    - Политики повторных попыток (Retries)?
    - Паттерн Circuit Breaker?
    - Паттерн Saga для распределенных транзакций?
    - Кеширование?
    - Стратегии fallback (запасные варианты)?

## 6. FAQ
**Q:** Можно ли взять свою тему?
**A:** Да, но ее необходимо предварительно согласовать с преподавателем. Тема должна быть достаточно сложной, чтобы обосновать декомпозицию на микросервисы.

**Q:** Обязательно ли использовать все паттерны, изученные на лекциях?
**A:** Нет. Нужно использовать только те, которые действительно подходят для вашей системы, и уметь обосновать их применение.

**Q:** Можно ли использовать одну монолитную базу данных для всех сервисов?
**A:** Нет. Принцип "Database per Service" является обязательным требованием лабораторной работы и одним из ключевых признаков микросервисной архитектуры.

**Q:** Нужно ли писать код в первой лабораторной работе?
**A:** Нет. Лабораторная работа №1 — это исключительно проектирование. Реализация будет происходить в Лабораторной работе №2.

**Q:** Обязательно ли использовать Kubernetes?
**A:** Нет. Kubernetes не требуется. Система может быть спроектирована для запуска через Docker Compose, что даже проще.

# Лабораторная работа №2: Реализация микросервисной системы

## 1. Цель работы
Реализовать микросервисную систему, спроектированную в Лабораторной работе №1, применив на практике паттерны и подходы, изученные в курсе. Получить опыт разработки распределенных систем с учетом вопросов надежности, безопасности и наблюдаемости (observability).

## 2. Описание задания
Необходимо реализовать систему, состоящую из 3–5 микросервисов (в соответствии с проектом из Лабы №1). Работа делится на 4 блока, каждый из которых посвящен определенному аспекту разработки. Результатом должен стать законченный продукт с бэкендом и фронтендом.

## 3. Общие требования
- **Формат работы:** в парах.
- **Инфраструктура:** весь проект должен запускаться на одной машине с помощью Docker Compose или Minikube.
- **Качество кода:** чистый код, понятные названия, структурированность проекта, комментарии там, где это необходимо.
- **Система контроля версий:** Git. Требуется нормальная история коммитов (не допускается единственный коммит с подписью "final version").

## 4. Структура оценивания
Работа разделена на 4 блока, максимальная оценка — **70 баллов**.

| Блок | Тема | Максимум |
|:---|:---|:---:|
| 1 | Межсервисное взаимодействие | 18 баллов |
| 2 | Данные и согласованность (consistency) | 17 баллов |

| 4 | Безопасность (Security) и Продакшн-готовность (Production) | 17 баллов |

### Правила приема блока
1.  **Обязательные пункты (Must Have):** Выполняются беспрекословно. Без их реализации блок не засчитывается.
2.  **Дополнительные пункты:**
    - Необходимо набрать минимум **1/3 от максимальной оценки блока** (т.е. не менее 6 баллов для блоков 1 и 3, и не менее ~5.7 баллов для блоков 2 и 4).
    - Сумма баллов за дополнительные пункты не может превышать **2/3 от максимума блока** (например, для 18-балльного блока нельзя получить больше 12 баллов за «допы»), даже если технически выполнено больше.

## Блок 2: Данные и согласованность (consistency) (17 баллов)

### Обязательные пункты (0 баллов)
- [ ] Реализован принцип **Database per Service** (каждый сервис работает с собственной базой данных).
- [ ] Используются **миграции БД** (Flyway, Liquibase, EF Migrations, Alembic). Схема данных версионируется и применяется автоматически при старте.
- [ ] Реализована **событийная согласованность (Eventual Consistency)** хотя бы в одном сценарии (как осознанный архитектурный выбор).

### Дополнительные пункты (нужно набрать минимум 6 баллов, макс. ~12)
- [ ] Применение паттерна **CQRS** (разделение моделей чтения и записи, оптимизация read-модели). **(5 баллов)**
- [ ] Реализация паттерна **Outbox** для гарантированной доставки событий (сохранение событий в outbox-таблицу в одной транзакции с данными, отправка через отдельный процесс). **(5 баллов)**
- [ ] Реализация паттерна **Inbox** для обеспечения идемпотентности обработки входящих сообщений (сохранение ID сообщений для игнорирования дубликатов). **(4 балла)**
- [ ] Реализация распределенной транзакции через паттерн **Saga** (хореография или оркестрация) с четкой последовательностью шагов. **(5 баллов)**
- [ ] Реализация **компенсирующих транзакций (Compensating Transactions)** в рамках Saga для отката выполненных шагов при ошибке. **(5 баллов)**
- [ ] Построение **Read-модели через проекции (Projections)** из событий (обновление материализованного представления при наступлении событий). **(4 балла)**
- [ ] Поддержка **версионности событий (Event Versioning)** для обеспечения обратной совместимости. **(4 балла)**
- [ ] Использование **распределенного кеша (Redis)** для кеширования часто запрашиваемых данных (паттерны Cache-aside или Read-through). **(4 балла)**

- [ ] Реализация паттерна **Bulkhead** (изоляция пулов потоков/соединений для предотвращения каскадных сбоев). **(4 балла)**
- [ ] Реализация **многоуровневого кеширования (Multi-level caching)** — L1 (in-memory) + L2 (Redis) с корректной инвалидацией. **(5 баллов)**

## 6. FAQ
**Q:** Можно ли использовать технологии, не указанные в списке?
**A:** Да, если они решают ту же задачу (например, Kafka вместо RabbitMQ).

**Q:** Обязательно ли делать все 4 блока?
**A:** Да. В каждом блоке нужно выполнить обязательные пункты и набрать минимум 1/3 от максимума за дополнительные.

**Q:** Можно ли использовать готовые примеры кода?
**A:** Как референс — да. Но итоговый код должен быть написан вами, и вы должны быть готовы объяснить его на защите.

**Q:** Сколько микросервисов нужно реализовать?
**A:** Минимум 3 (согласно обязательным требованиям блока 1).

**Q:** Нужно ли писать тесты?
**A:** Не обязательно, но это повышает качество работы и может дать бонусные баллы.

**Q:** Обязательно ли использовать Kubernetes?
**A:** Нет, Kubernetes не является обязательным. Это дополнительный пункт. Можно обойтись Docker Compose.

**Q:** Как засчитывается Saga, если у нас всего 3 сервиса?
**A:** Главное, чтобы была четкая последовательность шагов через 2-3 сервиса и реализованы компенсации при ошибке.

**Q:** Обязательна ли защита?
**A:** Да, без демонстрации работы и ответов на вопросы работа не засчитывается.
